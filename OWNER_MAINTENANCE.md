# Орбита — резервирование и управляемая очистка

**Включать только после тестирования SQL и отдельного подтверждения владельца.**

## Архитектура

- `src/OwnerDatabase.jsx`: раздел виден только роли `owner`, изолирован от интерфейсов преподавателей.
- `supabase/maintenance.mjs`: авторизация на сервере, шифрование AES-256-GCM с PBKDF2 SHA-256, закрытое хранилище и сверка копии после загрузки.
- `supabase/migrations/007_owner_maintenance.sql`: закрытый storage bucket и `orbita_maintenance` RPC; EXECUTE отозван у `PUBLIC`, `anon`, `authenticated`, доступен только `service_role`. RPC `SECURITY INVOKER`, вызывается исключительно из `calendar-api` после проверки owner.
- `supabase/handler.mjs`: маршруты `maintenance/*` добавлены перед `bootstrap`, с требованием действующей Auth-сессии и роли `owner`.

## Формат копии

Зашифрованный файл `.orbita` содержит UUID и полные строки таблиц групп, занятий, истории импортов, аудита и безопасные метаданные профилей. Поля Auth (хеши паролей, токены и секреты) **не** включены. Копии AES-256-GCM хранятся в **приватном** bucket `orbita-private-backups`, скачиваются владельцем в браузере. Копии по умолчанию **не удаляются**, даже после очистки рабочего журнала.

**Пароль шифрования необходимо хранить отдельно от Supabase:** без него копию нельзя расшифровать. Восстановление `merge` или `replace` возвращает строки `orbita_groups`, `orbita_lessons`, `orbita_imports`. Действующие Auth-аккаунты, профили и аудит не перезаписываются. Для групп, у которых отсутствует реальный профиль преподавателя в Auth, восстановление отклоняется (вместо тихого повреждения связей). При восстановлении из чужого проекта отказывается по project ID.

## Очистка и подтверждение

1. Только owner получает точный предпросмотр с подписью, связанной с текущими UUID/версиями.
2. Owner повторно вводит свой пароль Auth, фразу `УДАЛИТЬ НАВСЕГДА` и независимый пароль для шифрования резервной копии.
3. Сервер создаёт полную копию и **сверяет** содержимое со Storage.
4. Postgres в одной транзакции проверяет подпись и либо удаляет выбранные строки вместе с зависимыми занятиями, либо откатывает изменения. Операция записывается в аудит в той же транзакции.
5. После операции браузер автоматически скачивает аварийную зашифрованную копию.

Режимы: корзина, архив, конкретная архивная группа, занятия по периоду, правила расписания, история импортов (отдельно), полный сброс групп и занятий. При очистке только **правил расписания** существующие занятия сохраняются.

## Известные ограничения

- Восстановление Auth-паролей и учётных записей не поддерживается. Нужно восстановить Auth отдельно.
- Профили и аудит экспортируются, но для безопасности сохраняются текущими при восстановлении журнала. Это указано в интерфейсе.
- Самостоятельный экспорт архивов с учётными данными запрещён; не помещать файлы `.orbita` в публичный репозиторий GitHub.
- Supabase может иметь автоматические платформенные резервные копии вне этого механизма.
- До реального включения желательно протестировать RPC на отдельном нерабочем проекте, включая прерывание транзакции и восстановление полного снимка.

## Проверка

1. `npm test` (включая `tests/maintenance.test.mjs`).
2. `node scripts/build-shared.mjs`.
3. Проверить адаптивность 320, 375, 390, 430, 768, 1024 и 1440 пикселей; навигацию, календарь и формы.
4. Применить миграцию и проверить `pg_proc` ACL, storage bucket public=false.
5. Для одного **синтетического** объекта в отдельной базе проверить создание копии → очистка → восстановление.
6. Отдельное подтверждение владельца перед публикацией в основной `main`.
